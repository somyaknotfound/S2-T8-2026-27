Threshold-Aware Similarity Caching for Named Data Networks

A cache that may answer with a similar object instead of the exact one saves hops, but only if the user accepts the answer. We show that the standard model of this badly underestimates delay, and we design request formats and a cache decision rule that fix it. We test everything at packet level in ns-3 with ndnSIM, under congestion and burst loss.

The project in one sentence. A bad answer from a nearby cache is not free, because it costs the user a whole retry; so the request should tell the cache what is good enough, or the cache should weigh a risky answer against the delay it measures upstream.

The problem in one picture

Normal caches answer only when they hold the exact object you asked for. Similarity caching relaxes that: on a miss, the cache returns the most similar object it has. Image search, recommendations and LLM "semantic caches" use this, because a close answer is often good enough.

The catch is that only the user knows what "good enough" means. Each user has a threshold s. If the returned object's similarity s′ is below s, the user rejects it, waits a retry interval δ, and asks again. In a network of caches, every cache on the path makes the answer-or-forward choice, and a wrong answer costs a full round of the loop below.

What the base paper did, and where it breaks

Base paper: R. Nakamura and N. Kamiyama, "Analysis of Similarity Caching on General Cache Networks," IEEE Access, vol. 12, 2024. It is the first work to measure similarity caching from the user's side over a path of caches. Each cache answers with its best match with probability α, else forwards; the origin always has the exact item. The paper derives the mean similar-content delivery delay:

E[D] = d≥ + (1/ρ − 1) · (d< + δ) ρ is the chance that one attempt brings an acceptable answer; d≥ and d< are the mean delays of an accepted and a rejected attempt. The number of attempts is geometric with mean 1/ρ.

They evaluate it numerically on a tandem of 5 caches and an origin, 1 ms per link, a catalogue of C = 100 items, B = 10 items per cache, δ = 10 ms. To keep the maths tractable they assume:

  1. one fixed α at every cache, applied even when the cache holds the exact item;
  2. links with unlimited bandwidth: no queueing and no loss;
  3. every retry sees freshly random cache contents, so attempts are independent;
  4. cache contents are a uniform random set of B items;
  5. no protocol and no packets: numbers only.

Our three findings about the paper

1. Eq. (6) is misprinted. It weights only the last-hop round trip; the paper's own figures use the cumulative one. With that correction we reproduce its Fig. 5(a): 9.96, 45.97 and 80.6 ms at s = 1 for α = 0.1, 0.5 and 0.9.

2. Eqs. (8) and (10) appear to describe two different caches. Eq. (8) lets a request pass a cache that would have returned an unacceptable item, which only a cache that knows s can do. Eq. (10) stops at any cache that answers, which is a blind cache. Eq. (8) turns out to be exactly right for our threshold Interests.

3. Independent retries hide a heavy tail. This is the core finding. A real cache does not change its contents in the 10 ms between two attempts, so a user whose nearby caches hold nothing acceptable gets the same rejected answers again and again. The model averages ρ first and then inverts it, 1/E[ρ]; with persistent contents the truth is E[1/ρ], and by Jensen's inequality E[1/ρ] ≥ 1/E[ρ], often by a lot.

A quick illustration with invented numbers: if half the users have ρ = 0.5 and half have ρ = 0.001, the average ρ is about 0.25, so the model predicts about 4 attempts. In reality half need 2 attempts and half need 1,000, an average of about 500. In our setting the worst case is a user whose 5 caches all hold nothing acceptable: an attempt succeeds only if all 5 forward, (1 − 0.9)5 = 10−5 at α = 0.9.

What we are solving

Problem statement. Given a Named Data Network of similarity caches whose users accept an answer only above their own similarity threshold, and whose upstream links may be congested and lossy, design the request signalling and a per-cache answer-or-forward rule that bound the number of retries and minimise the mean delay until an acceptable answer arrives. Derive this delay in closed form where possible, and validate the design at packet level in ns-3 with ndnSIM.

Our three rules

All three replace the paper's coin flip at the Answer? step. They differ in what the request carries and what the cache must know.

Threshold

Tell the cache what is good enough.

Interest carries
The user's threshold, smin=s
Cache rule
Answer only if s′ ≥ s
Guarantee
Nothing is ever rejected: exactly one attempt. The paper's Eq. (8) becomes exact, and α = 1 becomes optimal.
Cost
Reveals each user's tolerance to every cache

Don't ask the same wrong cache twice.

Interest carries
On a retry, excl= the caches whose answers were rejected
Cache rule
Blind coin α, but a listed cache always forwards
Guarantee
At most (caches on the path + 1) attempts
Cost
Still wastes the first wrong answers

Delay-aware

Answer only when it is worth the risk.

Interest carries
The exclusion list and a HopLimit; never s
Cache rule
Compare the expected cost of answering with the cost of forwarding (below)
Guarantee
Adapts to load and loss with no knowledge of s; an exact hit is always served
Cost
Must learn, so it makes some rejections while learning

The delay-aware rule

A cache at h hops from the client has a best match with similarity s′. Answering costs the round trip Rh now; with probability 1 − F(s′) the user rejects it, which costs δ, the round trip again, and then the upstream delay. Forwarding costs Rh + D̂up. Answer when answering is cheaper:

(1 − F(s′)) · (δ + Rh + D̂up) < D̂up F(s′): share of this cache's users who accept similarity s′. D̂up: smoothed delay of forwarding, measured like TCP's SRTT (gain 1/8); an expired Interest counts as the time lost, so it also sees loss.
  • Direction. When the upstream is congested or lossy, D̂up rises, the bar for answering drops, and the cache answers locally more. That helps the user and also takes load off the bottleneck.
  • Position. A cache close to the origin sees a small D̂up and stays strict. The paper observed this position effect; our rule derives it.
  • Learning F. 20 similarity bins with a Laplace prior, fitted to be non-decreasing. A retry that names this cache in its exclusion list counts as a rejection; no retry within 1 s counts as an acceptance. The cache explores a bin only while its verdict is still uncertain at F ± 2 standard errors.

How we simulate it in a realistic network

This is a simulation, not a deployment on physical routers. But it is a packet-level simulation of a real protocol stack: real NDN packets go through NDN's real forwarding code, over links with finite bandwidth, queues and loss. The base paper had none of that; it only evaluated formulas.

How we know the simulator is right

  • Against closed forms. Every cell is compared with an exact analytical value, using the mean over at least 5 independent seeds and a 95% confidence interval (Student's t over runs).
  • Accounting identity. Each of the 1.27 million Stage 3 requests satisfies delay = 2τ × hops + δ × (attempts − 1), plus 0.7 to 1.7 µs of serialisation per hop.
  • Replay. Each new stage first replays earlier runs byte for byte, so a change in one part cannot silently move older results.
  • Independent cross-check. The closed forms are implemented twice, in Python and in MATLAB.

Results

1. The simulator reproduces the paper

2. Persistent contents create a heavy tail

Shown in the chart in the base-paper section: at α = 0.9 and s = 1 the paper predicts 80.6 ms, while ns-3 with persistent contents measures 14,522 ± 2,070 ms. 22% of requests reach the 5,000-attempt cap, and the 99th percentile is 51.2 s. The paper's conclusion that a large α evens out fairness is drawn exactly where this tail is worst.

  • As designed: D̂up rises with load and the learned threshold s* falls, so caches answer locally more. When idle, the cache next to the origin (v5) is the strictest.
  • At high load it reverses: v5's forwards all cross the congested backhaul, so it sees the largest D̂up and becomes the most lenient.
  • Stability: after warm-up the delay shows no significant drift at any load, and up to 0.9 load no cache's s* moves more than 0.03 between requests 1,000 and 2,000.
  • The mean s* of 0.77 is a mixture. At 0.95 load a cache flips between s* ≈ 0.95 and "answer anything" (s* ≈ 0) when D̂up spikes: 20% of snapshots at v5. Never quote 0.77 as a threshold it settled on.
  • Side effects: other traffic on the backhaul is barely affected (its delay differs by at most 5.5 ms between policies at 0.95 load, and is lowest under our rule, 50.9 ms). The price of learning is rejections: 0.13 per request when idle, 0.50 at 0.95 load. The oracle has none.

Retry cap at the clientThe proposal said the Interest would carry it. With the threshold in the Interest nothing is rejected, so a cap on the wire would never fire.

Answers to the questions you will get

What is new compared with the base paper?
A packet-level evaluation that did not exist; the size of the tail that independent retries hide; Interests that remove retries and make the paper's Eq. (8) exact; and a delay-aware rule that works under congestion and loss.
NDN only delivers Data whose name matches the Interest. How do you return a different object?
The answer keeps the Interest's own name; its payload says which item it is and how similar. NDN's matching is untouched, and NFD is unmodified.
NDN removed Selectors. Where does the threshold go?
In ApplicationParameters, the packet format v0.3 way to pass parameters; NDN then appends a digest to the name.
Why does the model underestimate the delay?
It averages the success probability, then inverts it. With persistent contents you must average the inverse, which is always larger (Jensen). At α 0.9 a user with no acceptable item nearby needs about 100,000 attempts.
Isn't sending the threshold trivial?
The header field is; the consequences are not: no retries, an exact closed form, α obsolete. It also leaks preferences, which is why we built the delay-aware rule.
Is a simulation a real network?
No, but it runs NDN's real forwarder over links with finite bandwidth, queues and loss, which the paper did not have. The strategy would port to a real NFD router once the similarity store moves out of the simulation controller.
Is the best-fixed-α baseline fair?
It is unfair to us: it picks the best α for each load after the fact, which no deployed cache can do, and we still win at every point.
Why ns-3 and ndnSIM?
The course allows UnetStack, ns-3 or MATLAB; ndnSIM is the NDN module for ns-3 and runs the real NFD forwarder.
